# Правила для агентов

Обязательны для каждого субагента. Цель — чтобы результаты параллельных агентов собрались в один проект без правок «на стыке».
Порядок чтения перед стартом: этот файл → свой раздел в [roles.md](roles.md) → [plan.md](../plan.md) (§3–§6) → код контрактов (`shared/types`, `app/entities/*/index.ts`, `app/shared`).

## 1. Источники истины

Приоритет при конфликте: **контракт в коде (после T0) > этот файл > plan.md > бриф роли > твои предположения.**

| Что | Где | Кто меняет |
|---|---|---|
| Типы домена и DTO | `shared/types/*` | только главный агент |
| Правила валидации | `shared/utils/validation.ts` | только главный агент |
| API сторов и сервисов | `app/entities/*/{model,api}`, сигнатуры — plan.md §4 | только главный агент |
| Имена компонентов | plan.md §3 | только главный агент |
| UI-контракт (тексты, роли, test id) | §6 этого файла | только главный агент |
| Токены дизайна | `app/assets/styles/tokens.css` | только главный агент |
| Зависимости, `nuxt.config.ts`, `tsconfig`, ESLint | корень | только главный агент (исключение: T5 добавляет `@playwright/test@1.62.0`) |

**Если контракта не хватает** (нужно поле, проп, событие, зависимость): не придумывай и не правь чужое. Сделай минимальный локальный обход, если он возможен в твоих файлах, и опиши ситуацию в отчёте блоком `CONTRACT GAP: что нужно → зачем → предлагаемое изменение`. Если без изменения контракта задачу не решить — остановись и верни отчёт.

## 2. Владение файлами

- Редактируешь только файлы своей роли (roles.md). Новые файлы создаёшь только внутри своих slice'ов.
- Чужие slice'ы — только чтение и импорт через их `index.ts`.
- Запрещено: менять `package.json` и lock-файл, конфиги, контракты; добавлять зависимости; удалять или переименовывать чужие файлы; трогать `docs/` (кроме T6).

## 3. Архитектура: FSD

- Слои и направление импортов: `app → pages → widgets → features → entities → shared`. Импорт только вниз.
- Slice'ы одного слоя не импортируют друг друга. Если нужна связь — композиция уровнем выше (слоты, пропсы).
- Каждый slice экспортирует публичный API через `index.ts`; извне импортируется только он: `import { PostCard } from '@entities/post'`.
  Внутри slice'а — относительные импорты.
- Структура slice'а: `ui/` (компоненты), `model/` (сторы, composables, типы slice'а), `api/` (сервисы), `lib/` (чистые функции). Пустые сегменты не создаются.
- Границы проверяет ESLint (`npm run lint`, `eslint.config.mjs`): глубокие импорты в slice, импорты вверх по слоям и между slice'ами одного слоя, импорт слоя через `~/` вместо алиаса, а также `console` и `v-html` — это ошибки. Если lint падает на границе, исправляй структуру, а не правило.
- Алиасы слоёв: `@shared`, `@entities`, `@features`, `@widgets` (→ `app/<layer>`). Импорты слоёв только через них: путь `~/<layer>` запрещён линтером. `#shared/` — корневой `shared/` с контрактами клиент ↔ сервер (типы, валидация), это не слой FSD `@shared`. `~/` остаётся для `app/assets`. Автоимпорт компонентов выключен — компоненты импортируются явно. Vue / Nuxt API (`ref`, `computed`, `useFetch`, `defineStore`, `navigateTo`) автоимпортируются. Исключение: модули с unit-тестами вне Nuxt-рантайма (`lib/*`, `feed.store.ts`, `validation.ts`) импортируют `vue` / `pinia` явно.

## 4. Код

**TypeScript**
- strict, без `any`, `@ts-ignore`, `as unknown as`; type guards вместо кастов.
- Именованные экспорты (кроме SFC и файлов, где Nuxt требует default).
- `interface` — для форм объектов, `type` — для union.

**Vue**
- Только `<script setup lang="ts">`. Порядок блоков: script → template → style scoped.
- Порядок в script: импорты → props / emits / slots → composables и сторы → локальный state → computed → функции → watchers → lifecycle.
- `defineProps<Props>()` с `interface Props` и `withDefaults` при необходимости. Булевы пропсы — `isX` / `hasX`. Пропсы не мутируются. `defineEmits` с типизированными кортежами.
- Презентационные компоненты (`shared/ui`, `entities/*/ui`) не обращаются к сторам и API. Сторы используют features, widgets и pages.
- Ключи в `v-for` — стабильные id, не индекс. `v-if` и `v-for` на одном элементе не совмещаются. `v-html` запрещён.
- Компонент — до ~150 строк и одна ответственность. Больше — дели.

**Именование**
- Компоненты — PascalCase.
- Папки slice'ов — kebab-case.
- Сервисы — `<entity>.service.ts`, экспорт `<entity>Service`.
- Сторы — `<name>.store.ts`, экспорт `use<Name>Store`.
- Composables — `useX`.

**Иммутабельность.** Состояние не мутируем на месте: `posts.value = posts.value.map(...)`, объекты — через spread.

**Ошибки.** Не глотаем: каждая ветка `catch` либо пробрасывает типизированную `ApiError`, либо переводит её в состояние UI с понятным текстом из UI-контракта. Без `console.log` и отладочного кода.

**Комментарии.** Только «почему», не «что». Код и комментарии на английском.

**Без оверкода.** Никаких абстракций «на будущее», интерфейсов с одной реализацией, фабрик, конфигов для констант, неиспользуемых экспортов.

## 5. Nuxt и SSR

- Первый рендер детерминирован: в шаблоне нет `Date.now()`, `Math.random()`, `window`, `localStorage`.
  Время — `<NuxtTime :datetime relative locale="en-US" />`. Id для ARIA — `useId()`.
- `useRoute()` из Nuxt. `route.fullPath` в разметке не используется.
- Данные страницы: `useAsyncData(key, () => xService.y())` со стабильным ключом.
  **Исключение — лента:** она в Pinia, потому что изменяемая (лайки) и общая для страниц. Вызов `if (import.meta.server) await feed.ensureLoaded(); onMounted(() => { void feed.ensureLoaded() })`: клиентская загрузка только после монтирования, иначе после SSR-ошибки первый клиентский рендер (скелетоны) не совпадёт с SSR-HTML (alert). Двойной запрос исключён гидрацией Pinia и guard'ом `ensureLoaded`.
- Мутации и действия пользователя — через сервисы (`$fetch` внутри `app/shared/api/http.ts`). Прямой `$fetch` в компонентах и сторах запрещён.
- `useCookie` вызывается только синхронно в setup (стор, composable, компонент), не после `await`.
- 404: `throw createError({ statusCode: 404, statusMessage: 'User not found', fatal: true })`.
- Адаптивность только через CSS (media queries 640 / 1024 px, mobile-first). JS-детект ширины запрещён: даёт hydration mismatch.

## 7. Стили и доступность

- Цвета, отступы, радиусы, тени, шрифты — только через CSS-переменные из `tokens.css`. Хардкод цветов запрещён.
  Брейкпоинты — литералы 640 / 1024 px (CSS-переменные не работают в media queries).
- `<style scoped>`; классы по смыслу (`.post-card__header`), без глобальных утилит.
- Семантика вместо ARIA там, где возможно. Кнопка — `<button type="button">`, переход — `<NuxtLink>`.
- Доступное имя у каждой интерактивной иконки. Декоративные SVG — `aria-hidden="true"`.
- Тач-цели ≥ 44 px (`--tap-size`). Видимый `:focus-visible`. Анимации отключаются при `prefers-reduced-motion`.
- Контраст AA: текст на оранжевом — тёмный (`--color-on-brand`), акцентные иконки — `--color-brand-strong`.
- `<img>`: `alt` (пустой для декоративных), `width` / `height` или `aspect-ratio`, `loading="lazy"` и `decoding="async"` (кроме первого экрана).

## 8. Рабочий процесс агента

1. **Окружение.** Работаешь в своём git worktree (ветка выдаётся при запуске). Первая команда — `npm ci --prefer-offline`. Dev-сервер — только на своём порту (T2 → 3002, T3 → 3003, T4 → 3004, T5 → 3005; раунд 2: A → 3012, B → 3013). E2E запускай на своём порту: `E2E_PORT=<порт> npm run test:e2e` (A → 3022, B → 3023). Останавливай сервер только по своему порту: `kill $(lsof -ti :<порт>)`. `pkill -f` запрещён: он убивает серверы других агентов.
2. **Понимание.** Прочитай контракты и код зависимостей. Если что-то неясно — смотри §1 (приоритет источников). Не угадывай API: проверь в коде.
3. **Реализация** строго в своих файлах и в рамках критериев приёмки plan.md §6.
4. **Самопроверка** (все пункты обязательны):
   - `npm run typecheck`, `npm run lint`, `npm run test` — зелёные;
   - `npm run build` проходит;
   - запусти `node .output/server/index.mjs` на своём порту и проверь свою страницу через `curl` (SSR-HTML содержит ожидаемое; для защищённых страниц подставь cookie `socio_session`);
   - пройди чеклист §4–§7 по своему диффу.
5. **Коммиты** — в свою ветку, 1–3 штуки, Conventional Commits из plan.md §7. Не пушить, не мержить, `main` не трогать.
6. **Отчёт** главному агенту — строго в формате §9.

**Круги доработки.** Замечания ревьюера → правка → повторная самопроверка. Максимум 3 круга, дальше эскалация главному агенту с описанием блокера.

## 10. Ревьюер

Ревьюер (отдельный субагент, только чтение) проверяет дифф ветки против: критериев приёмки plan.md §6, UI-контракта §6, правил §3–§7, импорт-правил FSD и SSR-безопасности.
Отчёт — список `[BLOCKER|MAJOR|MINOR] файл:строка — проблема → исправление`, отсортированный по важности. В конце — вердикт `merge` или `rework`. Стилистические мелочи без влияния на поведение и поддержку не репортятся.
