# Social Network — Nuxt 4

Перенос ядра Flutter-приложения [Social-Network-UI-Made-In-Flutter](https://github.com/stevie1mat/Social-Network-UI-Made-In-Flutter) на **Vue 3 + Nuxt 4 + TypeScript**.

Сквозной сценарий: **вход → лента → карточка публикации → профиль пользователя**. Вёрстка адаптивная: мобильная ширина от 360 px и десктоп.

## Быстрый старт

Нужен Node 24 (проверено на 24.15) и npm.

```bash
npm ci
```

```bash
npm run dev
```

Приложение откроется на http://localhost:3000. Вход — как в оригинале: подходит любой корректный email и пароль от 6 символов, например `allan@example.com` / `secret123`.

| Команда | Что делает |
|---|---|
| `npm run dev` | dev-сервер |
| `npm run build` / `npm run preview` | production-сборка и её запуск |
| `npm run lint` | ESLint, включая границы слоёв FSD |
| `npm run typecheck` | `vue-tsc` по приложению, серверу и тестам |
| `npm test` | unit-тесты (Vitest) |
| `npm run test:e2e` | e2e (Playwright, Chromium): сам собирает приложение и поднимает его на порту 3005 |

Перед первым запуском e2e нужно один раз скачать браузер:

```bash
npx playwright install chromium
```

## Что перенесено

**Вход** (`/login`)
- Поля email и пароль с валидацией и текстами ошибок из оригинала: при отправке и после ухода с поля.
- Переключатель видимости пароля, «Remember me», индикатор загрузки на кнопке.
- Ошибка входа показывается в форме (`role="alert"`), форма остаётся рабочей.

**Оболочка приложения**
- Шапка с логотипом, навигацией и аватаром.
- На мобильной ширине навигация уходит в нижний бар, как BottomNavigationBar в оригинале. Переключение только на CSS, без определения ширины в JS.
- Вкладки «Home» и «Profile»; активная вкладка выделена не только цветом.
- Тонкая оранжевая полоса загрузки при переходах между страницами и собственный индикатор загрузки (три точки) вместо кольца в духе Material.

**Лента** (`/`)
- 30 постов. Первые 6 — те же типы контента, что в оригинале, остальные собраны из них же:
  - «X is now connected to Y and N others» с фото;
  - то же с галереей;
  - check-in без вложения;
  - пост с sound byte;
  - пост с фото;
  - пост с видео-превью.
- Подгрузка при прокрутке страницами по 6 (курсорная пагинация, `IntersectionObserver`), в конце «You're all caught up.». Скринридер слышит «Loaded 6 more posts.».
- Состояния ленты: скелетоны при загрузке, ошибка с кнопкой «Retry», пустая лента. Ошибка подгрузки показывается под уже загруженными карточками, у неё свой «Retry».

**Карточка публикации**
- Автор и время публикации («1 hour ago»), текст и вложение.
- Like со счётчиком, Bookmark (обе кнопки с `aria-pressed`) и счётчик комментариев.
- Имя автора, его аватар и упомянутые в активности люди — ссылки на их профили. Аватар скрыт от скринридера и Tab, чтобы не дублировать ссылку по имени.
- Время публикации и счётчик комментариев открывают страницу поста. Кликабельной всю карточку не делали: внутри уже есть кнопки и ссылки, а на мобильном при прокрутке были бы случайные открытия.

**Страница поста** (`/posts/:id`)
- Карточка и комментарии (только чтение).
- Лайк и закладка общие с лентой: лайкнули на странице поста — в ленте тоже лайк, и наоборот.
- Прямая ссылка работает через SSR. Неизвестный пост — страница 404, остальные ошибки показываются на странице с «Retry».
- Кнопка «Back»: назад по истории, при прямом заходе — в ленту.

**Профиль** (`/users/:id`)
- Аватар, имя, роль, компания и город; статистика (followers, following, posts) и bio.
- Связи (connections) со ссылками на их профили и список sound bytes.
- Кнопка «Log out» видна только в своём профиле.
- На чужом профиле кнопка «Back»: назад по истории (лента остаётся на месте прокрутки), при прямом заходе — в ленту. Cmd/Ctrl/Shift+клик открывает ленту в новой вкладке, как у обычной ссылки.
- Пока профиль грузится, показывается скелетон в его форме.
- Неизвестный пользователь — страница 404 со ссылкой на ленту. Остальные ошибки показываются прямо на странице с кнопкой «Retry».

**Сессия**
- Глобальный middleware не пускает гостя дальше `/login` и после входа возвращает на исходный адрес (`?redirect=`, только внутренние пути).
- Без «Remember me» сессия живёт до закрытия браузера, с ним — 30 дней.

## Что исправлено по сравнению с оригиналом

Подробный разбор — в [docs/analysis.md](docs/analysis.md), §6. Коротко:

| В оригинале | Здесь |
|---|---|
| Logout не работает: после `pushReplacement` гейт авторизации выпадает из дерева | Logout очищает сессию, middleware отправляет на `/login` |
| Неуспешный вход всё равно пускает в приложение, ветка ошибки недостижима | Ошибка показывается в форме, навигация только после успеха |
| `PostProvider` с лайками и закладками написан, но нигде не подключён | Like и Bookmark работают через Pinia-стор; лайк сохраняется при переходе в профиль и обратно |
| Из ленты нельзя попасть в профиль автора | Автор и упомянутые люди — ссылки на `/users/:id` |
| «Remember me» ничего не делает | Определяет срок жизни cookie сессии |
| Несогласованные моки (Allan Paterson / Scott Hamilton), `bio` игнорируется | Единая мок-база в `server/utils/mock-db.ts` |
| Пиксельное позиционирование (`Positioned(left: 150)`) | Адаптивная вёрстка: токены, flex/grid, mobile-first |
| Белый текст на оранжевом (~2:1) | Контраст по WCAG AA: тёмный текст на оранжевом |

## Что намеренно не перенесено и почему

| Что | Почему |
|---|---|
| Stories, Meetup с картой, Notifications, Connections (вкладки) | Вне ядра, ТЗ их явно исключает. Вкладки нижнего бара сокращены до Home и Profile, без пустых заглушек |
| Декор карточек ленты: наложенная визитка контакта (телефон, email) и бейдж ♥ на фото, меню «…»; в check-in — аватары «5 Joining» и карта с кнопкой «Meet Up» | Статичные элементы без поведения, а карта и Meet Up относятся к исключённому Meetup. Check-in перенесён как текст активности с местом |
| В профиле: таймлайн «My activity», отдельный экран Profile Details с приватными данными (email, телефон, адрес) и кнопкой Edit, «View All» у связей | Роль, компания и город подняты в шапку профиля. Профиль теперь открывается для любого пользователя, поэтому приватные данные API не отдаёт вовсе. Edit и View All в оригинале ничего не делают |
| Добавление комментариев и Share | В UI оригинала это кнопки без действия. Комментарии можно читать на странице поста, а добавление и Share требуют записи на сервер, которой у мока нет (см. «Следующие шаги») |
| Сохранение лайков на сервере | Мок-сервер не хранит состояние, лайк живёт в сторе до перезагрузки страницы. Серверного лайка не было и в оригинале |
| Заглушки на логине: Forgot Password, Sign Up, вход через Facebook / Google / Apple, кнопка «назад» | В оригинале только показывают snackbar «… coming soon!». Ошибки входа вместо snackbar показываются в форме |
| Оригинальный логотип и ассеты | Вместо логотипа — нейтральный оранжевый знак: перенос брендинга не влияет на сценарий. Фото — с picsum.photos и randomuser.me |
| Pixel-perfect и анимации (fade + slide на логине) | По ТЗ не требуется; сохранены композиция, палитра, шрифты (Lato, Urbanist) и иерархия |

## Архитектура

Feature-Sliced Design, слои импортируют только вниз: `pages → widgets → features → entities → shared`.

```
app/
  pages/            index (лента), login, users/[id], posts/[id]  — тонкие, только композиция
  layouts/          default (шапка + нижний бар), auth
  middleware/       auth.global.ts — гейт авторизации
  widgets/          app-header, bottom-nav, post-feed, post-details, user-profile
  features/         auth-by-email, logout, toggle-like, toggle-bookmark
  entities/         session, post, user — api (сервисы), model (сторы), ui
  shared/           api (http-клиент), ui (кнопка, аватар, иконки…), lib, config
server/
  api/              auth/login.post, feed.get, posts/[id].get, users/[id].get — мок-бэкенд на Nitro
  utils/            mock-db.ts, mock-posts.ts — данные и искусственная задержка
shared/             контракты клиента и сервера: типы и валидация
tests/              unit (Vitest) и e2e (Playwright)
```

- **Типы** лежат в корневом `shared/types` и общие для клиента и сервера, поэтому контракт API один. Вложение поста — discriminated union (`image | gallery | video | sound-byte`). В Flutter для этого было 6 почти одинаковых виджетов карточки.
- **API и сервисы.** `shared/api/http.ts` — `$fetch` с единым `ApiError`. Сервисы сущностей (`post.service`, `user.service`, `session.service`) — единственное место, где знают URL.
- **Публичный API slice'а** — только `index.ts`. Слои подключаются через алиасы `@shared`, `@entities`, `@features`, `@widgets`.
- **Границы проверяет ESLint**: глубокие импорты, импорты вверх и между slice'ами одного слоя — ошибка. Автоимпорт компонентов выключен, зависимости видны явно.

## Ключевые решения при переносе Flutter → Vue/Nuxt

| Flutter | Vue / Nuxt | Почему |
|---|---|---|
| Provider + ChangeNotifier | Pinia setup-stores | Ближайший аналог, работает с SSR и гидрацией |
| AuthWrapper — виджет-гейт | Глобальный route middleware | Проверка до рендера и на сервере, без мигания экранов |
| `Navigator.push` / `pushReplacement`, индекс вкладки в state | File-based routing, URL — источник состояния | Работают deep link, «назад» и обновление страницы; именно `pushReplacement` ломал logout в оригинале |
| Имитация API внутри провайдера | Nitro server routes | Настоящая граница client ↔ server, загрузка и ошибки проверяются честно, бэкенд можно заменить без правок UI. Задержки 300–600 мс вместо 2 с у входа в оригинале: состояния загрузки видны, но не тормозят |
| Сессия в памяти | Cookie (`useCookie`) | Доступна при SSR, переживает перезагрузку, реализует «Remember me» |
| Лента в провайдере | Pinia-стор + SSR | Лента приходит в HTML и гидрируется; на клиенте грузится после монтирования, чтобы гидрация совпала с SSR даже при ошибке. Стор защищён от устаревших ответов (generation counter) |
| 6 захардкоженных виджетов карточек | Курсорная пагинация `GET /api/feed?cursor=`, нормализованный стор (записи по id и порядок ленты), sentinel с `IntersectionObserver` | Страницы дописываются без дублей. Лайк на странице поста и в ленте — одна запись. Курсор лежит в SSR-payload, поэтому гидрация не расходится |
| Профиль | `useAsyncData` с реактивным ключом | Данные в SSR-payload, при переходе между профилями нет гонок; 404 — fatal-ошибка → `error.vue` |
| `copyWith` | Иммутабельные обновления через spread | Тот же принцип, покрыт unit-тестами |
| Валидаторы внутри `TextFormField` | Чистые функции в `shared/utils` | Одна логика на клиенте и сервере, тестируется отдельно |
| `MediaQuery` и пиксели | CSS-токены, flex/grid, брейкпоинты 640 / 1024 px | Адаптивность без JS и без hydration mismatch |

**Доступность**: семантические заголовки и landmarks; у всех полей есть label; у кнопок-иконок есть имена; `aria-pressed`, `aria-current`, `aria-busy`; видимый фокус; цели нажатия не меньше 44 px; контраст AA.

## Тесты и проверки

- **Unit (Vitest), 153 теста:**
  - валидация;
  - `safeRedirect` (open redirect: `//evil`, `/\evil`, абсолютные URL);
  - иммутабельные toggle-функции;
  - feed-стор: повторной загрузки нет, гонки ответов, reset, подгрузка без дублей, правило слияния;
  - мок-база: пагинация, курсоры, 400 на плохой ввод, комментарии;
  - форматирование чисел, инициалы, `isPlainClick`.
- **E2E (Playwright)**: 22 сценария в двух профилях — desktop 1280×800 и mobile 390×844:
  - редирект гостя;
  - валидация, переключатель пароля и ошибка входа;
  - вход с индикатором загрузки и 6 карточками;
  - лайк и отмена лайка;
  - переход в профиль и сохранение лайка при возврате;
  - перезагрузка профиля;
  - logout;
  - deep link после входа;
  - 404;
  - бесконечная прокрутка до 30 постов и ошибка подгрузки с «Retry»;
  - страница поста: переход по времени, прямой SSR, inline-ошибка, лайк синхронен с лентой, 404;
  - аватар ведёт в профиль и пропускается клавиатурой;
  - «Back» в профиле и на посте: по истории и при прямом заходе, Shift+клик открывает новое окно;
  - скелетон профиля при медленном ответе.

  Тесты блокируют внешнюю сеть и падают на ошибках в консоли браузера.
- `lint`, `typecheck`, `build` проходят. CI не настраивался: в рамках задания всё проверялось локально.

## Где использовались ИИ-инструменты

Проект сделан в **Claude Code** по схеме «ведущий агент + субагенты». Решения по архитектуре и процессу принимал я, ИИ работал под моим контролем.

2. **План.** Агент составил [docs/plan.md](docs/plan.md): объём работ, архитектуру, контракты API и UI, критерии приёмки, e2e-сценарии.
   - План прошёл раунд критики, все замечания сведены в таблицу трассировки (§8).
   - Архитектуру (FSD, алиасы слоёв, проверка границ в ESLint) утверждал я.
3. **Правила для агентов.** Агент написал [docs/agents/rules.md](docs/agents/rules.md) и [docs/agents/roles.md](docs/agents/roles.md): владение файлами, UI-контракт, стандарты кода, процесс и формат отчёта. Так результаты параллельных агентов гарантированно стыкуются.
4. **Реализация.**
   - Фундамент (T0) делался первым.
   - Затем четыре трека шли параллельно, каждый в отдельном git worktree и своей ветке: вход и оболочка, лента, профиль, e2e.
5. **Ревью.**
   - Каждую ветку проверял отдельный субагент-ревьюер (`vue-reviewer`, только чтение) по критериям приёмки. Замечания уходили на доработку: цикл «реализация → ревью → правки».
   - Ведущий агент проверял отчёты и сводил противоречия. Пример: где задаётся ширина контента — в layout или на странице.
   - Ведущий агент делал интеграционную сборку, мержил ветки в линейную историю и проверял живой сценарий в браузере на обеих ширинах.
6. **Раунд 2 — улучшения после сдачи ядра.** Список улучшений задал я: больше постов с подгрузкой, кнопка «назад», страница поста, профиль по клику на аватар, свой лоадер. Дальше тот же цикл:
   - ведущий агент заложил контракты и план (`docs/plan.md` §10);
   - критик нашёл в плане 4 серьёзные проблемы до начала работы. Например, параметр `?limit=` тихо сломал бы перехват запроса в старом e2e, а курсор вне `ref` терялся бы после SSR;
   - два трека шли параллельно, каждый прошёл ревью. У «Back» нашёлся дефект: Cmd/Ctrl-клик уводил текущую вкладку вместо новой. Его исправили, а заодно ту же ошибку на странице 404;
   - ведущий агент проверил ветки пробной интеграцией, пока шло ревью, затем смержил их.
7. **README** написан ведущим агентом по итогам работы.

### Дальше: перенос остальных экранов оригинала

Ядро задумано как основа для полного переноса. Каждый экран добавляется по одной схеме:
- контракт в `shared/types`;
- мок-эндпоинт в `server/api`, позже его заменит настоящий бэкенд без правок UI;
- slice'ы `entities`, `features`, `widgets` и страница-композиция;
- тот же цикл, что и для ядра: план → критика → параллельные треки → ревью → e2e.

По мере переноса нижний бар возвращается к пяти вкладкам оригинала, у каждой вкладки свой маршрут.

Порядок — от дешёвого и переиспользующего готовое к тяжёлому:

| # | Экран | Что делаем | Оценка |
|---|---|---|---|
| 1 | **Connections** (вкладка; ссылка в шапке ленты и «View All» в профиле) | `pages/connections`, виджет списка связей на готовой `entities/user`, фича `connect` / `disconnect`. API — `GET /api/users/:id/connections` с пагинацией, `POST` и `DELETE /api/connections/:id`. Счётчики в профиле обновляются | ~0,5 дня |
| 2 | **Notifications** (вкладка; `NotificationProvider` в оригинале уже есть) | `entities/notification`, виджет ленты уведомлений, фича «прочитано», бейдж непрочитанных на вкладке. API — список с курсором и отметка о прочтении. Следующий шаг — realtime через SSE | 0,5–1 день |
| 3 | **Профиль целиком**: Profile Details, Edit, My activity | Страница деталей: приватные поля (email, телефон, адрес) API отдаёт только владельцу. Форма редактирования — фича `edit-profile`, валидация в `shared/utils`, как у логина. Таймлайн «My activity» на CSS вместо пакета `timeline_tile` | ~0,5 дня |
| 4 | **Создание поста и комментарии** (`createPost`, `addComment`, `sharePost` из `PostProvider`) | Фичи `create-post` (текст и фото), `add-comment` на готовой странице поста, `share`. Оптимистичные обновления в нормализованном сторе ленты | ~1 день |
| 5 | **Stories** (лента сверху, `status.dart`) | Виджет полосы историй и просмотрщик с прогрессом, автопереходом и свайпами. Оригинал грузит истории напрямую с GitHub raw. У нас сервер проксирует и кэширует только фиксированный allowlist URL, клиент во внешний источник не ходит | ~1 день |
| 6 | **Meetup и карта** (вкладка и карта в check-in карточке; `flutter_map`) | Карта на Leaflet и OSM: компонент только для клиента (`<ClientOnly>`, ленивый импорт), чтобы не тянуть его в SSR и общий бандл. В `PostAttachment` добавляется тип `map`, фича `join-meetup` («Meet Up») | 1–1,5 дня |
| 7 | **Sign Up, Forgot password, вход через соцсети** | Нужен настоящий бэкенд (п. 1 выше): фичи `register` и `reset-password`, OAuth-провайдеры. До этого экраны не переносим, чтобы не плодить заглушки | после бэкенда |

Итого полный перенос оригинала — примерно 5–6 рабочих дней поверх текущего ядра, не считая настоящего бэкенда.

### Известные ограничения

- Лайки и закладки не переживают перезагрузку страницы (см. п. 2).
- Если профиль не загрузился на сервере не из-за 404, страница отдаёт статус 200 с ошибкой и кнопкой «Retry». Так сделано намеренно, чтобы временный сбой не превращался в страницу ошибки.
